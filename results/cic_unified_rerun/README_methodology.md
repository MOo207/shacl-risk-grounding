# CIC-IDS2018 Unified Rerun — Methodology

Generated by `scripts/build_cic_unified_rerun.py`. No LLM/API calls were made in this
task — dataset construction, feature engineering, and non-LLM ML baselines only.

## Context

A sibling investigation on NSL-KDD found two problems in that pipeline: (1) the
NL-description generator leaks the true attack class name directly into the prose
the LLM reads (30/50 cases affected, safety-significance evaporates when excluded),
and (2) NSL-KDD's XGBoost baseline is not run-to-run reproducible (48% prediction
match across two runs with the same seed/data/features). This directory audits
CIC-IDS2018's unified-ablation pipeline for the same two problems and prepares
matched fresh samples for a future dataset-unified LLM rerun.

## 1. XGBoost reproducibility — VERIFIED REPRODUCIBLE, no fix needed

Retrained the exact `build_unified_ablation_testset.py` pipeline (same seed=42
train/eval split, same `XGBClassifier(random_state=42)`) twice from scratch and
compared predictions on the 180-case eval sample to (a) each other and (b) the
frozen historical `results/unified_ablation/test_set.json::xgb_predicted_class`.

**Result: 180/180 = 100% match** in all three comparisons (run1-vs-run2,
run1-vs-frozen, run2-vs-frozen). xgboost 3.2.0, scikit-learn 1.6.1.

This is the opposite of the NSL-KDD finding. The likely reason: CIC-IDS2018's
training pool is orders of magnitude larger than NSL-KDD's, and the histogram-based
tree construction with a fixed `random_state` on both the `train_test_split` and the
`XGBClassifier` is deterministic at this scale on this machine/xgboost version. No
diagnosis or fix (tree_method pinning, n_jobs, column-order) was required — see
`xgboost_baseline_results.json::reproducibility` for the full numbers.

## 2. Leakage audit — two distinct channels, audited over the existing N=60 LLM-evaluated subset

The audited subset is the 60 case_ids (10/class) that actually appear in
`results/unified_ablation/pure_llm.jsonl` — this is CIC's existing "N=60" LLM
comparison set referenced in the task, a stratified subset of the full N=180 pool.

**(a) NL-description channel — 22/60 (37%) leaky — SAME category of problem as NSL-KDD.**
`scripts/_archive/run_slm_nl_classification.py::features_to_nl()` contains five
hand-written signature branches that template the attack-category name directly
into the generated prose (e.g. "denial-of-service (DoS) attack tools",
"distributed denial-of-service (DDoS) flooding tools", "automated HTTP brute-force
credential stuffing", "automated web attack tooling", "associated with
infiltration"). This is a templated label insertion identical in kind to NSL-KDD's
generator. It is *partially* mitigated for the tri-stage LLM arms
(`tristage_llm_haiku`/`tristage_llm_sonnet`) because those arms are already given
the ML-predicted attack class explicitly in the prompt, so NL leakage adds no new
information there — but it matters directly for `pure_llm`, where the attack class
is withheld and must be inferred from the NL description + CVE alone.

**(b) CVE-description channel — 21/60 (35%) leaky — a different, more defensible situation, but not zero.**
The paired CVE descriptions are real third-party vulnerability summaries (not
synthetic prose written by this pipeline), so a CVE "being about" a DoS bug and
literally containing "DoS" is inherent to CVE-grounded framing rather than an
artifact of experiment design. However it is measurable and non-trivial: the small
`CVE_BY_CLASS` candidate pool means **all 3 DoS-class CVEs** (CVE-2007-6750,
CVE-2009-0696, CVE-2011-3192) literally contain the substring "DoS", so every DoS
case is CVE-leaky by construction; BruteForce is partially leaky (1 of 2 candidate
CVEs contains "brute-force" literally); WebAttack and DDoS CVE text contains no
literal class token.

**Union: 33/60 (55%) leaky by either channel.** Full per-case tags, trigger text,
and by-class breakdown are in `leakage_audit.json`.

Recommendation for the redesign: report the two channels separately (as done
here), since they carry different epistemic weight. If a fully leakage-free
`pure_llm` arm is required, paraphrase/redact the class-naming clause from CVE
descriptions before they reach the LLM, and rewrite the five signature branches in
`features_to_nl()` to describe the same tabular evidence without naming the attack
category (mirroring the NSL-KDD remediation).

## 3. Fresh non-overlapping samples

Drawn from `data/processed/cleaned_dataset.csv` after first reproducing the
*original* 180-row reservation (same code/seed as `build_unified_ablation_testset.py`)
to identify and exclude those rows — no row-level ID existed in `test_set.json`, so
exact-reproduction-then-exclusion is the only way to guarantee zero overlap.

- **`calibration_sample.json`** — 60 cases (10/class), seed=42, for future
  LLM-override-threshold tuning only. NOT scored in the final comparison.
- **`test_sample.json`** — 120 cases (20/class), seed=43 (distinct RNG stream from
  calibration, drawn from the pool with calibration rows already removed) — the
  actual held-out evaluation set for the eventual rerun.

Verified disjoint: `calibration_sample.json` ∩ `test_sample.json` = ∅, and both are
disjoint from the original 180-row `test_set.json` eval set (by construction, since
both draw from a pool with those rows pre-removed).

Each case carries the same fields as the original pipeline (asset, `paired_cve`,
`nl_description` via the exact same `features_to_nl()`, `feature_subset`,
`xgb_predicted_class`/confidence/risk_level, `ground_truth_risk_level`,
`criticality`) so they are ready to feed to an LLM later — no new prompt content
was invented.

The ML model (XGBoost) used to label these samples was trained on the pool
excluding ALL reserved rows (original 180 + calibration 60 + test 120) — zero
leakage by construction.

## 4. Held-out XGBoost baseline safety metrics (`test_sample.json`, N=120)

Using the identical NFCRM §6.9 risk-level mapping and metric definitions as
`scripts/tag_nslkdd_leakage_and_clean_subset.py`:

| Metric | Value |
|---|---|
| Exact match | 95.0% |
| Within ±1 level | 96.7% |
| Under-escalation rate | 3.3% (4/120) |
| Over-escalation rate | 1.7% |
| Severe recall (High/Catastrophic GT correctly flagged severe) | 96.6% (57/59) |
| Worst miss (levels under-escalated) | 4 |

(Calibration-sample XGBoost metrics, reference only — not part of the evaluation:
exact 88.3%, under-escalation 8.3%, severe recall 94.7%.)
